# 随机抽奖算法审查与修复报告（v2.0.1）

日期：2026-09-13 · 范围：common 抽奖核心 + 6 平台开箱链路（v1_21_1 / v26_1_2 / v26_2 /
forge_26_1_2 / forge_26_2 / forge_1_20_1）· 对应 CHANGELOG `[2.0.1] - Unreleased`

## 1. 审查结论（A）

### 1.1 服务端权威抽奖链路（正确性 ✅）

- **档位抽取** `OddsCalculator.precomputeWeights/pickGrade`：只累加正权重（`long` 求和防
  溢出），`nextBoundedLong` 用拒绝采样保证无偏（`bound ≤ Integer.MAX_VALUE` 时走
  `random.nextInt`，大权重走 rejection）。测试覆盖 3×`Integer.MAX_VALUE` 与预计算路径
  序列一致性。
- **档内物品抽取** `GradeMap.pickWeighted` / `TerminalSession.pickWeightedIndex`：同一无偏
  实现 + 线性扫描加权，`weight <= 0` 的条目在池子构建时即被移除（作者可临时禁用单件）。
- **动画条** `BoxStripGenerator`：50 格独立掷骰，`winningIndex` 固定在 [35,44] 且回退到
  最近有效格；**中奖格物品 = 实际发放物品**，动画与结果一致（单开与批量首箱均验证）。
- **批量开箱**：每箱独立 seed 独立掷骰；首箱动画条与后续箱子共用同一保底/权重语义；
  异步计算后主线程重验证库存、只发放实际可用数量。
- **显示层** `BoxOdds` 与掷骰层共用 `precomputeWeights`，档位概率口径一致。

### 1.2 边际点（非当前可触发崩溃，记录备查）

1. `pickGrade` 在无正权重时返回档 1 —— v2.0.1 起由「平台拒开」闸门兜住，不再静默出 1 档。
2. `BoxStripGenerator` 展示档位 clamp 到 [1,5]，掷骰未 clamp——当前 `GRADE_COUNT=5` 无触发
   路径；若未来支持 6+ 级权重（`MAX_GRADES=64` 上限存在）需同步。
3. `GradeMap.pickWeighted` 的 `total<=0` 均匀回退分支为防御性死代码（构造已过滤）。
4. `nextBoundedLong(bound<=0)` 会抛 IllegalArgumentException——所有调用点当前都保证 `bound>0`。

## 2. 修复（B）

### 2.1 【真实 bug】JEI/REI/EMI 显示概率与真实抽取不一致

v2.0.1 引入档内物品 `weight` 后，三款配方面板的「单件概率」仍按档内均匀计算，与实际
加权抽取不符（加权配置时误导玩家）。修复：`BoxOdds` 新增加权感知入口
`itemChance(gradeChance, itemWeight, itemCount, positiveItemWeightSum)`（全 1 权重时数值
与旧均匀公式完全一致），10 个显示文件改用按物品下标的加权概率：

- v1_21_1 / forge_1_20_1：`jei/BoxOpenCategory`、`rei/BoxOpenCategory`、`emi/BoxEmiRecipe`
- v26_1_2 / v26_2：`jei/BoxOpenCategory`、`rei/BoxOpenCategory`
- forge_26_1_2 / forge_26_2：无显示层插件，无需改动

新增 `BoxOddsTest` 均匀/加权/禁用条目/全零权重 4 组断言。

### 2.2 全零权重语义修正（C1）

旧行为：`random` 全为 0/负时 `pickGrade` 静默返回档 1（整箱只掉 1 档，作者配置错误被掩盖）。
v2.0.1：单开与批量在**掷骰前**用 `BoxOdds.hasOpenableWeights` 拒绝请求且不消耗钥匙/箱子；
`BoxJsonSchemaValidator.validateRandom` 对全非正权重输出「箱子不可掉落」提示（不阻断加载，
`/csbox validate` 可见）；box-editor 文案同步更新。改动覆盖 6 平台 12 处守卫 + 校验器 +
`BoxJsonSchemaValidatorTest` 3 组新断言 + `BoxOddsTest.hasOpenableWeights`。

## 3. 新特性（C）—— 开箱保底（pity）

### 3.1 配置

```json
{
  "type": "csbox",
  "random": [625, 125, 25, 6, 4],
  "pity": { "grade": "classified", "every": 20 }
}
```

- `grade`：保底目标档 id（consumer/industrial/mil_spec/restricted/classified）。
- `every`：连续 `every-1` 次开出低于目标档后，下一次**强制**从目标档及以上按档位权重抽取。
- 命中（结果 ≥ 目标档，含强制触发）即重置计数；内存态按「玩家 × 箱子」计数，重启清零
  （与 `max_per_player`/`cooldown_seconds` 同生命周期）。
- 配置非法（未知档位 / `every < 2`）静默降级为无保底，校验器提示。

### 3.2 实现

- `common/logic/PityPolicy`：纯策略（`of/ofLevel/shouldForce/nextStreak`），无 MC 依赖。
- `common/logic/PityTracker`：`ConcurrentHashMap` 内存计数（单开主线程与批量异步池共用），
  提供 `missStreak/recordOpen/startStreak/finishStreak/reset`。
- `OddsCalculator.pickGradeWithPity`：触发时对 `[targetLevel..5]` 切片按原权重抽取；
  切片无正权重（作者把目标档权重配 0）时安全回退普通抽取，绝不强制出空。
- 平台接线（每平台 BoxDefinition + BoxJsonLoader + 单开 + 批量）：
  - `BoxDefinition` 新增 `Optional<PityPolicy> pity`（网络编码：bool + 2 int；非法值读入
    时 `ofLevel` 返回 null → 无保底）。
  - `BoxJsonLoader` 解析 `pity` 对象 → `builder.pity(PityPolicy.of(grade, every))`。
  - 单开：掷骰前快照 streak；`shouldForce` 时用 `pickGradeWithPity` 重掷中奖格（物品 +
    档位同步替换动画条对应格）；**发放成功后才** `PityTracker.recordOpen` 推进计数。
  - 批量：批次开始时 `startStreak` 快照，`computeKResults` 内维护批内本地 streak（首箱
    动画条同样支持强制替换），`finalizeBulkOpen` 仅在全部发放成功后按实际结果重算并
    `finishStreak` 写回（中途取消/被拒不推进计数）。
- `box.schema.json` 新增 `pity` 定义（grade 枚举 + every ≥ 2）；box-editor model 透传
  （不再丢失该字段）、校验器 + 双语文案 + 表单输入支持；`docs/CONFIGURATION.md` 字段表
  与行为说明更新。

### 3.3 评审后口径修复（fix-B / fix-D / fix-A）

- **fix-B（计数口径统一为 roll grade）**：`PityTracker.recordOpen / PityPolicy.nextStreak`
  的输入从「解析/兜底后的最终档位」改为「掷出的档位」——单开路径新增 `pityRollGrade`
  快照；批量路径新增 `BulkOpenResult.pityGrade` 字段贯通 compute → finalize。效果：
  强制 roll 落在目标档、但物品池 fallback 换成了低档物品时，这次仍计为命中（保底承诺
  不再被物品解析链吞掉）。
- **fix-D（空结果不推进）**：批量 `computeKResults` 内只有非空结果推进批内 streak，
  与 `finalizeBulkOpen` 写回时跳过空结果的口径一致。
- **fix-A（永不触发的保底可见化）**：`BoxJsonSchemaValidator.validatePity` 校验
  `pity` 形状（grade 枚举 / every ≥ 2 / 非对象 / 缺字段），并检测「random 中目标档及以上
  权重全零 → pity 永不触发」，在 `/csbox validate` 中提示。
- **fix-E/fix-C（PityTracker 加固，common 层）**：写入全部改为单 per-key `compute`
  原子读改写；条目带最后触碰时间戳，每 2048 次变更清扫一次（7 天未触碰删除）；
  100k 硬上限 + 最旧批次逐出（极端兜底 clear）——内存不再随玩家数无限增长。
- **fix-F（批量种子统一 SecureRandom）**：`PacketCsgoBulkProgress` 的批量 seed（首箱 + 
  后续每箱）从 `ThreadLocalRandom` 改为 `SecureRandom`，与单开路径同一安全随机源。
- **fix-A（loader 运行时告警）**：各平台 `BoxJsonLoader` 在解析 `pity` 后校验
  `[targetLevel..5]` 权重和，≤0 时 `recordLoadWarning`（热重载路径也能看到）；
  与 `BoxJsonSchemaValidator.validatePity` 的 `/csbox validate` 提示互为补充。
- **随机源加固（种子安全）**：终端机会话（`TerminalSession` ×6）、实体掉落判定
  （`ModEvents` ×6）与谈判模型（common `NegotiationModel`）的默认 `new Random()`
  全部改为 CSPRNG 种子派生；`PacketCsgoProgress` 固化「serverSeed 不得写日志/发
  客户端/经事件暴露」约定（48 位 LCG 持种子即可复现）。多人世界下所有随机入口均为
  独立不可预测种子，不存在「多人同种子」；全量 grep 确认 0 处裸 `new Random()`。
- 已知取舍（记录不修）：pity 计数为内存态（重启清零/集群不可共享）；`missStreak` 读 +
  `recordOpen` 写非原子（当前由 10 tick 开箱冷却兜底）；批量 seed 用 `ThreadLocalRandom`
  （非加密安全，64 位难推断）。以上如需产品化（持久化/原子化/存储级别随机）可作为
  后续迭代。

### 3.3 测试

- `PityPolicyTest`：解析/非法配置/触发阈值/命中重置/批量往返（PityTracker）。

## 5. 遗留/建议

- pity 计数为内存态：重启清零（已在 schema/CONFIGURATION 注明）；如需跨重启保底，
  建议后续把计数并入玩家数据/持久化存储（本版刻意不做，保持与服务端约束一致）。
- `BoxStripGenerator` 的 grades clamp 与「6+ 级权重」支持可作为独立需求跟进。
- 终端机抽奖（`TerminalSession`）未接入保底（终端是购买语义，非开箱），若需要可另行扩展。

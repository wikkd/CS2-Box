01最严重的一条：奶油主题的副文本几乎读不清

这是本次审计唯一一个会直接影响每一位访客的问题，也是唯一一个仅靠阅读源码无法发现的问题—— 静态分析给出的数字是 3.3:1，而真实渲染只有 1.98–3.59:1。

实测数据

HIGH H1 · 副文本坐在橙色背景图上，对比度低至 1.98:1 既有问题
现象
所有用 --muted 着色的说明性文字（副标题、页脚、版本提示、帮助文字、路径提示、行内小标签） ——在浅色主题下几乎糊在背景里。

版本提示12px#8b8374rgb(229,182,67)1.98:1失败
路径提示12px#248f8ergb(236,181,50)2.08:1失败
页脚说明12px#8b8374rgb(253,191,60)2.27:1失败
顶栏副标题12px#8b8374rgb(253,204,85)2.49:1失败

标签页 / 顶栏按钮12–14px#38332brgb(252,223,160)9.66:1通过
根因
两层因素叠加，缺一不可：
  1. 页面背景是一张橙色照片，只罩了很薄的奶油色。 css/style.css:1109–1117（最终生效的 body 规则）： 
    body {
  background:
    linear-gradient(rgba(250, 246, 236, .16), rgba(250, 246, 236, .26)),  /* 仅 16%–26% 罩层 */
    url('../img/bg.jpg') center / cover no-repeat fixed,                  /* 橙色原图直接露出 */
    radial-gradient(...);
}
    bg.jpg 实测为强橙色（放大后约 rgb(213,150,60) 系）， 而罩层仅 16%–26%，所以背景的**真实亮度远高于**调色板里的奶油色 #f4f0e6。
  2. --muted 这个颜色本身太浅。定义于 css/style.css:889： --muted: #8b8374，对纯奶油 #f4f0e6 只有 3.30:1—— 即使背景理想也已不达标；叠上橙色背景后进一步跌到 1.98:1。 该变量在全站被引用 61 处。
归属
既有问题，与本次会话的改动无关。--muted: #8b8374 由 ec0e0f71 feat(box-editor): cream glassmorphism theme 引入； 薄罩层由 57308cda style(box-editor): liquid glass — much more transparent, stronger frosted blur 引入。 对照实验：禁用全部动画/过渡/模糊后复测，数值完全一致（--muted: #8b8374、opacity: 1）， 证明与动效层无关。
建议
需要两层一起改，只改一处不够：
  • 提罩层：把 body 的奶油罩从 16%–26% 提到约 55%–70%（或对 bg.jpg 自身降饱和/提亮）， 让背景稳定落在浅色区间。这是设计取向的取舍——毛玻璃质感会变弱。
  • 压暗 --muted：对纯奶油达标的最小改动是 #746d61（4.50:1）， 留余量可取 #6f695c（4.79:1）。若要直接扛住当前橙色背景，则需深到 #5c564c 一类， 但那会让「次级文字」看起来过重——所以更合理的是先做上一步。
  • 另可选：给这些文字所在容器补一层不透明底（如 .foot、.version-note）， 使其不再直接压在照片上。改动面最小，视觉副作用也最小。

02无障碍：两处对键盘 / 读屏用户的实质阻断

HIGH H2 · 切换预览视图时 aria-selected 永不更新 既有问题
现象
点击 Probabilities / Simulator 后画面正确切换，但读屏仍播报「JSON，已选中」。
实测
aria-selected before : view-json=true  view-prob=false  view-sim=false
aria-selected after  : view-json=true  view-prob=false  view-sim=false   ← 未变
.active       after  : view-json=-      view-prob=active  view-sim=-     ← 视觉已切换
线上生产环境结果一致。
根因
js/app.js:2335 setPreviewView() 只切换 CSS 类，未写回 ARIA 状态： 
if (jsonTab) jsonTab.classList.toggle('active', previewView === 'json');
if (probTab) probTab.classList.toggle('active', previewView === 'prob');
if (simTab)  simTab.classList.toggle('active', previewView === 'sim');
而 aria-selected 是写在 index.html:77–79 的静态属性，此后无人维护。
建议
在同一个函数里同步 setAttribute('aria-selected', ...)；同时给三个面板补 role="tabpanel" 与 aria-controls（见 M3）。改动约 6 行，无视觉影响。
HIGH H3 · 文件列表的切换目标不可聚焦，键盘用户无法切换箱子文件 既有问题
现象
左侧文件列表里，点击一行会切换当前编辑的文件。但这一行不是可聚焦元素， 键盘用户 Tab 只能停在行内的「重命名 / 删除」按钮上——没有任何键盘路径能切换到另一个文件。
实测
{"tag":"DIV","tabindex":null,"role":null,"focusable":false,"innerButtons":3} （线上一致）。全站 tabindex 使用次数为 0。
根因
js/app.js:624 生成的是 <div>，而切换逻辑挂在容器的点击委托上： 
return '<div class="file-item' + (active ? ' active' : '') + '" data-file-id="...">' + ...

// app.js:668
const item = e.target.closest('.file-item');
if (item) switchFile(item.dataset.fileId);
switchFile 全站只有这一处调用点（app.js:669）， 且 app.js 中仅存在两个 keydown 监听（:887 与 :1558），均与文件列表无关。
建议
把外层改为 <button type="button">（或用 href 无关的 role="option" + tabindex="0" + Enter/Space 处理）， 行内三个操作按钮去除嵌套冲突即可。这是三处 HIGH 里修起来最简单、收益最直接的一处。

03中等问题

MEDIUM M1 · :focus-visible 规则漏掉表单控件，下拉框几乎没有焦点提示 既有问题
根因
css/style.css:1293–1297 的焦点样式只枚举了 5 个选择器，没有 select / input / textarea： 
.btn:focus-visible,
.tab:focus-visible,
summary:focus-visible,
.example-item:focus-within,
.col-head:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
实测
按 Tab 依次遍历，前两个停靠点是顶栏的两个下拉框，与后续按钮的表现明显不同： 
1. SELECT#lang-select     :focus-visible=true  outline=3px none  shadow=rgba(47,111,219,0.14) 0 0 0 3px   ← 仅 14% 透明度，近乎不可见
2. SELECT#version-select  :focus-visible=true  outline=3px none  shadow=rgba(47,111,219,0.14) 0 0 0 3px   ← 同上
3. BUTTON#btn-undo        :focus-visible=true  outline=2px solid  shadow=none                          ← 正常
4. BUTTON#btn-theme       :focus-visible=true  outline=2px solid  shadow=none                          ← 正常
建议
把 select, input, textarea 加入上表选择器列表（或改用 :where(input, select, textarea, button, summary):focus-visible 统一覆盖）。
MEDIUM M2 · 全站没有任何 aria-live 区域 既有问题
实测
aria-live / role="status" / role="alert" 计数 = 0（线上一致）。 该工具的核心反馈——操作成功/失败的 Toast、校验错误列表、概率表刷新——对读屏用户全部静默。
建议
给 Toast 容器加 role="status" aria-live="polite"，错误类用 role="alert"； 给校验结果区加 aria-live="polite"。
MEDIUM M3 · tablist 与面板之间没有建立 ARIA 关联 既有问题
实测
{"live":0,"panels":["-","-","-"],"controls":[null,null,null]}。 index.html:76–79 已正确地写了 role="tablist" / role="tab"， 但三个 role="tab" 都没有 aria-controls， 三个面板（#json-preview / #prob-panel / #sim-panel）也都没有 role="tabpanel"——等于声明了标签页结构却未接上面板。
建议
补齐 id ↔ aria-controls 对应与 role="tabpanel"。 （完整 APG 还要求 roving tabindex + 方向键，该项列为 LOW，见 L7。）
MEDIUM M4 · 没有 beforeunload 保护，大段编辑可能无声丢失 既有问题
实测
addEventListener 类型清单仅 load, hashchange, storage，无 beforeunload。 状态虽会自动落 localStorage（这点做得不错，实测能从损坏的状态块中恢复）， 但用户在误关标签页 / 误刷新前得不到任何确认。
建议
当状态与上次保存快照不一致时挂上 beforeunload（浏览器要求返回 event.preventDefault()）。
MEDIUM M5 · 暗色主题漏了一处奶油色背景，反而比浅色主题更糟 既有问题
根因
奶油层给 .item-adv 设了浅色底（style.css:1019 的 .28、:1169 的 .2）， 但暗色主题的覆盖规则 只重设了 border，没有重置 background： 
html[data-theme="dark"] .item-adv {
  border: 1px dashed var(--border);
  border-radius: 6px;
}                     /* ← 缺 background，于是 rgba(255,253,248,.2) 残留 */
html[data-theme="dark"] .item-adv .adv-badge { color: var(--accent); }
实测
线上暗色主题下 details.item-adv 的背景仍为 rgba(255, 253, 248, 0.2)—— 深色界面里出现一块发白的面板；其中的 .adv-badge（rgb(61,139,255)）压在这块淡底上只有 2.77:1，而同一元素在浅色主题下是 4.54:1。深色主题比浅色主题更差，属明确的主题奇偶性缺陷。
建议
在暗色覆盖里补 background: rgba(255,255,255,.04) 一类深色底即可。
MEDIUM M6 · 内部开发文档 README.md 随站点公开发布 既有问题
实测
HEAD https://wikkd.github.io/CS2-Box/README.md → 200，8,050 B（本地 dist 一致，16,999 B 源文件）。 同一响应里还确认 sw.js 也对外可访问（这一项是正常的，Service Worker 本就必须公开）。
根因
box-editor/build.mjs:13–28 的 FILES 数组把 'README.md' 列为拷贝项， 于是它进入 dist/ 并被 GitHub Pages 发布。该 README 是面向开发者的 17 KB 说明（含内部结构与构建说明）。 package.json / build.mjs / server.mjs / tests/ / start.bat 均已正确排除（404）。
建议
从 FILES 中移除 'README.md'。风险评级为「中」是因为它不涉及密钥， 但把内部文档默认公开属于信息暴露面管理问题。

04我引入的改动：净改善，但有 3 组组合变差

REGRESSION L1 · 响应式改动整体压低了顶栏，但 320/360 中文与 414 英文反而高了 32px 本次会话引入
这一条我先给出了错误结论，特此更正。 基于「上一轮记录的 166px 基线」与「320px 实测 198px」的对比，我最初判定为「顶栏由 166px 长到 198px」。 随后把 0f091faa~1（改动前）与 0f091faa（改动后）的样式表并排托管、 在 10 个宽度 × 中英双语下逐一对测，结论完全不同：20 组里有 15 组顶栏变矮，只有 3 组变高。 上一轮记录里的 187px / 234px 是英文读数，我误当成中文读数去比，才得出「净变高」的结论。

净结论：改善 15 组，退化 3 组，持平 2 组。 最大改善是 768px 中文下的 −57px，以及修掉了 1181–1280 区间原先 50px 的粘性遮挡。 退化的 3 组全部是 +32px（恰好两行控件），集中在 320 / 360 中文与 414 英文。

副作用
上一轮改动的设计目标是「换取高度确定性」，代价是顶栏高度开始明显依赖语言——因为中英文标签宽度不同， 换行行数随之变化。这一点改动前后都存在，但出现的位置被移动了：
  • 改动前语言差异最大处：320px（zh 166 vs en 241，差 75px）、1024px（110 vs 150，差 40px）
  • 改动后语言差异最大处：414px（zh 123 vs en 198，差 75px）、320px（198 vs 235，差 37px）
最好的情况下最差组合仍达 235px（320×640 视口的 37%），这种「同一份界面在不同语言下高度差 75px」 本身就是一个应当收敛的问题，而不是我这次能顺手解决的。
为什么当初选择换行
上一轮实测：11 个控件自然宽约 924px，而前两个（语言 + 版本下拉）就占 291px—— 360px 上若用「单行 + 横向滚动」，只会露出这两个下拉，把撤销/新建/导入/示例/分享全推出屏幕。 用 order 把按钮提前可以修正视觉顺序，但会破坏 DOM 与焦点顺序（WCAG 2.4.3），因此否决。
建议
三种方向，取舍不同，需要你定：
  • 收起为图标 / 溢出菜单（推荐）：小屏下把语言 / 版本 / 主题收进一个「⋯」菜单，主操作保留图标按钮。 顶栏可回到 2 行以内，并顺带消掉语言差异——需要新增少量 CSS 与一个弹出菜单。
  • 高度封顶：给 .topbar-controls 设 max-height 并让多余控件横向滚动， 即「换行 + 滚动」折中，保证顶栏高度有上界。
  • 恢复单行滚动：需同时把语言 / 版本下拉收窄到合计 ≲180px（实测 291px 是爆宽主因）， 否则仍会把主要动作挤出屏幕。

06复核中被剔除的误报（探针自身的缺陷）

下列 4 类结论在第一轮自动扫描中曾被标记为问题，逐条复核后判定为我的探针缺陷，不计入问题清单。 列出是为了让你知道哪些曾被怀疑、以及为什么最终否定。

曾报出的结论复核结果探针缺陷
.price-table / .entity-empty 是死代码（0 个匹配） 误报。价格页 .price-table = 1；清空实体后 .entity-empty = 1。 两者都是条件 / 路由相关渲染。 探针只在 index.html 加载态查询一次
.w24 是死代码 误报。由 app.js:2057 在条目行的 NBT 输入框上条件渲染。 同上，未覆盖全部渲染分支
「顶栏背景不透明（alpha=0），内容会透出」× 11 个视口 误报。顶栏是刻意设计的毛玻璃：linear-gradient(rgba(255,252,244,.42), rgba(248,243,232,.34)) + backdrop-filter: blur(18px) saturate(1.8)。内容透出是设计意图，不是缺陷。 只读了 backgroundColor，未读 background-image 与 backdrop-filter
「50+ 个控件无无障碍名」 误报。修正后仅 5 个（见 L6），且全部为隐藏元素。顶栏各按钮均有可访问名。 取可访问名的函数漏了 textContent 分支
「暗色主题 6 个文本角色对比度不足」 误报。该轮把主题切反了（colorScheme=dark 下应用默认就是暗色， 再点切换反而回到浅色），量的其实是浅色主题。修正后暗色主题仅「路径提示」不达标。 未先读取当前主题就执行切换

07结论与建议顺序

总体判断：这个编辑器的工程质量是扎实的——零依赖离线可用、双主题、i18n 无缺项（data.js 的 zh/en 配对完整）、39 个输入框注入 HTML 载荷后全部正确转义（无 HTML 注入）、 能从损坏的 localStorage 状态块中恢复、无重复 id、无未捕获异常、无控制台错误、 各视口横向溢出恒为 0。问题集中在无障碍的收尾与一处配色决策上，而不是架构层面。

08附录：测量方法

覆盖范围

  • 页面：index.html、prices.html
  • 环境：本地 dist/（npm run build 产物，15 文件 / 422,363 B） 与线上 https://wikkd.github.io/CS2-Box/（全新浏览器 profile，无 SW 缓存）
  • 视口：320×640 至 2560×1440 共 11 组，横竖屏混合
  • 主题：奶油（默认）与暗色，两套独立测量
  • 浏览器：Chromium（Playwright 1.63.0，项目 devDependency）

对比度的像素法

第一版用「逐级合成祖先背景色 alpha」计算，结果系统性偏乐观——因为它看不见 background-image。改为：

  1. scrollIntoViewIfNeeded() 确保元素在视口内；
  2. 取元素包围盒，page.screenshot({clip}) 截取真实渲染像素；
  3. 自写 PNG 解码（zlib.inflateSync + 反过滤），计算每像素相对亮度；
  4. 取亮度中位数作为有效背景色（文字像素是少数，中位数落在背景上）；
  5. 与计算样式的 color 求 WCAG 对比度。

该方法把 H1 从「3.30:1 不达标」修正为「1.98–3.59:1 严重不达标」，并且解释了原因—— 背景是橙色照片而非奶油色。

对照实验

为排除「本次会话新增的动效层影响测量」，对同一组元素做了禁用全部 animation / transition / backdrop-filter 的对照复测： 

control (all animation/transition/blur disabled):
  muted:   #8b8374
  versionNote:  rgb(139, 131, 116)
  foot:         rgb(139, 131, 116)
  brandP:       rgb(139, 131, 116)
  pathHint:     rgb(36, 143, 142)
  opacityOfVersionNote: 1
  transformOfVersionNote: none

与未禁用时完全一致，确认 H1 与动效层无关。

前后对测（A/B）

为判断「顶栏高度变化」到底是我引入的回归还是改善，做了严格的同环境对测：

  1. 把 dist/ 复制两份；
  2. 用 git show 0f091faa~1:box-editor/css/style.css 取出改动前的样式表，覆盖其中一份； 打印两者行数（2942 vs 3146）确认确实不同；
  3. 两份都以 file:// 打开，在 10 个宽度 × 中英双语下各量一次顶栏高度与横向溢出。
踩到一个 Windows 陷阱，导致第一次 A/B 结果全为「0px 差异」： Node 的 execSync 在 Windows 上经由 cmd.exe 执行，而在 cmd 里 ^ 是转义字符——我写的 0f091faa^ 被吃成 0f091faa， 于是「旧版」取回的其实是新版自身，两份产物完全一样，看起来就像「改动毫无影响」。 改用 0f091faa~1 后即得到真实差异。任何在 Windows 上通过 execSync 调用 git 的地方都要避开 ^。

其他验证手段

  • 焦点环：清空焦点后逐次 Tab，记录每个停靠点的 matches(':focus-visible')、outline-*、box-shadow
